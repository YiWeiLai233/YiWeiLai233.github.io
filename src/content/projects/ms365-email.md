Microsoft 365 企业邮箱是给公司做的一整套办公基础设施，采购、域名绑定、租户配置、邮箱开通、DNS 认证和后续运维都由我一人完成。它不像写代码那样有提交记录可查，但踩过的坑一个不少——尤其是邮件这件事，配置错了不会立刻报错，而是几周后发现自己发的邮件全进了别人的垃圾箱。

## 项目定位

目标很朴素：让公司有一个看起来正规的邮箱，`info@` 能收客户来信，员工之间有统一的通讯录和日历，对外发信不被判成垃圾邮件。

之所以选 Microsoft 365 而不是自建邮件服务器，是因为自建邮件最麻烦的不是收信，而是**发信信誉**：新 IP 没有历史、没有反向解析、没有认证链，发出去的邮件大概率被拒或被降级。商业邮箱自带这些信誉背书，省下的运维精力远超订阅费用。

## 核心能力

- 域名邮箱：以公司自有域名作为邮箱后缀，`info@` 作为对外统一入口。
- Exchange Online 托管：收发信、日历、通讯录、共享日历与自动回复都在云端。
- DNS 认证链：SPF 授权发信源、DKIM 对邮件签名、DMARC 声明处理策略。
- 邮箱管理：账号开通与停用、别名与转发、容量与保留策略。
- 客户端贯通：Outlook 桌面端、移动端与网页版的统一登录与自动发现。
- 合规与安全：多重身份验证、可疑登录告警、外部发件人标识。

## 技术结构

整体是"权威 DNS + 云端邮箱"的两段式结构，本地方不存任何邮件数据。

域名解析在阿里云（`dns11/dns12.hichina.com`），邮箱在 Exchange Online。两者之间靠一组 DNS 记录绑定，最关键的四类：

- **MX** 指向 `hapticsys-com.mail.protection.outlook.com`（优先级 1），声明收信投递到微软；
- **TXT（SPF）** 为 `v=spf1 include:spf.protection.outlook.com -all`，授权微软的发信服务器，并以 `-all` 拒绝其余来源；
- **TXT（租户验证）** 形如 `MS=msXXXXXXXX`，用来证明域名归属，验证通过后即可删除；
- **CNAME（DKIM）** 形如 `selector1._domainkey` → `selector1-<租户>.onmicrosoft.com`，把公钥托管在微软侧。

客户端侧靠 `autodiscover` 记录自动找到服务端点，用户只需要输入邮箱和密码，不需要手填服务器地址。这个"看不见"的环节恰恰是体验的分水岭：少了它，每次换设备都要教用户填服务器。

## 值得复盘的地方

**一是 SPF 的 `-all` 和 `~all` 差别很大。** `~all` 是软失败，邮件仍会投递但打标记；`-all` 是硬失败，未授权的发信源直接拒收。授权了就要硬拒，否则等于留了个口子给伪造发信人。代价是**以后接任何第三方发信服务都必须同步加进 SPF**，漏加就是发不出去。

**二是 DKIM 的记录容易配成"看起来有、实际没生效"。** 如果域名上存在泛解析（`*` 记录），查询 `selector1._domainkey` 会返回一个 A 记录而不是 CNAME —— 从命令行看"解析是通的"，但微软侧永远读不到公钥，签名校验一直失败。要确认 DKIM 真的启用，必须看邮件原文里的 `DKIM-Signature` 头，而不是看 DNS 能不能查出来。泛解析会让所有这类"记录缺失"的问题伪装成"配置正常"，这是个很隐蔽的陷阱。

**三是 DMARC 是最容易被跳过的一条。** SPF 和 DKIM 配完，很多人就以为结束了。没有 DMARC 记录，收件方不知道"校验失败时该怎么办"，也不会给你发聚合报告——你既拿不到可见性，也拿不到保护。上线顺序应该是先 `p=none` 收报告，看几周数据确认正规发信源都通过了，再切到 `p=quarantine` / `p=reject`，直接上拒绝会把内部正常邮件也拦掉。

**四是租户验证记录留存会误导后来人。** `MS=ms...` 那条 TXT 验证完就没用了，留着不会报错，但下次有人翻 DNS 会以为某个环节还依赖它。配置类工作应该顺手清理冗余记录。

**五是企业邮件的运维成本主要在"人"不在"技术"。** 开通账号、配置转发、处理离职交接、清理超容量邮箱——这些操作本身简单，但它们决定了邮箱能不能被真正用起来。技术上跑通只算完成了一半。

## 后续维护方向

- 补齐 DKIM 的两条 CNAME，并清理泛解析，让签名校验真正生效。
- 添加 DMARC 记录，从 `p=none` 起步，积累报告后再收紧策略。
- 把 SPF 里后续接入的第三方发信源统一纳入维护清单，避免漏加导致发信失败。
- 建立离职与转岗的账号处理清单，包括邮箱转换、别名保留与数据交接。
- 定期检查邮箱容量与登录审计，处理长期未登录账号。

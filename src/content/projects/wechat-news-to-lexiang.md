`wechat-news-to-lexiang` 是一个自包含的 WorkBuddy Skill，当前版本 v2.4.0，2187 行代码与文档，纯 Python 标准库、零第三方依赖，打出来是一个 39 KB 的 zip。

它解决的问题是：群里每天发一堆公众号和技术资讯，看到了、存了链接，然后从不回看。想让机器把正文读完提炼成能检索的精读稿，而不是再造一个链接清单。

## 链路

```
链接 → 抓正文 → AI 读全文 → 精读稿（一篇一文件）→ OneDrive + 乐享
```

链路里唯一不是自动的一环是「拿到链接」，这一环永久留给人工：用户贴链接，或者把清单存成文件喂给 `collect.py`。

## 核心能力

- **抓正文**：普通 HTTP 请求带浏览器 UA，对 `mp.weixin.qq.com` 直接返回完整 HTML。不需要 Playwright，也不需要登录态。
- **五段式精读稿**：一句话 / 它解决什么问题 / 怎么做 / 关键数据 / 值不值得读。结构固定不是格式洁癖——它是产出质量的分界线。
- **一篇一文件**：不做一天一份合并 md。一篇塞十条，知识库检索时 RAG 召回会返回一整天的流水账。
- **标题简写命名**：取正文 H1 冒号前的主标题，清掉 Windows 非法字符，超长截断。`六大具身路线详解：模块化、技能编排、IL、RL、VLA…` 落成 `六大具身路线详解.md`。
- **双存储**：本地 OneDrive 同步目录 + 乐享知识库（每日资讯 / 按月分目录）。
- **同名不覆盖**：四步判据区分「同篇重跑」和「不同文章撞名」，后者另存为 `<简写>-<日期>.md`。
- **环境自检**：`check_env.py` 一次查完 Python 版本、配置、OneDrive 目录是否真在同步根下、乐享配置是否完整，用 `[OK]` / `[!]` / `[X]` / `[-]` 标状态，退出码 1 表示有阻断问题。

## 技术结构

```
wechat-news-to-lexiang/
├── SKILL.md                      主指令：流程、写作规范、踩坑、排错
├── 安装与配置.md                  给 agent 的执行清单
├── 安装说明.md                    给人看的使用说明
├── config.example.json           配置模板（不含个人数据）
├── scripts/
│   ├── check_env.py              环境自检
│   ├── collect.py                投喂文件解析（不读聊天记录）
│   ├── fetch_articles.py         抓公众号正文
│   ├── publish.py                同步 OneDrive，标题简写命名，同名不覆盖
│   ├── setup_onedrive.py         路径配置向导
│   ├── test_collect.py           投喂解析自测（7 项）
│   └── test_publish.py           命名与同名冲突自测（10 项）
└── references/
    └── lexiang-mcp-setup.md      乐享 MCP 配置
```

所有脚本的根目录就是 Skill 自己，`config.json` 与 `SKILL.md` 同级，缺失时从 `config.example.json` 自动生成。判断标准只有一条：**把整个文件夹复制到另一台机器，能不能直接跑。**

## 能力边界

边界是写死进 SKILL.md 的，不是留给 agent 临场判断：

| 环节 | 可行性 | 说明 |
|---|---|---|
| 拿到链接 | **靠人工投喂** | 个人微信无官方 API，也不读本地聊天库 |
| 抓公众号正文 | **完全可以** | 纯 HTTP，不需要浏览器 |
| AI 提炼内容 | 可以 | 这一步决定整份产出的价值 |
| 写 OneDrive | 可以 | 写本地同步目录，无需 Microsoft 授权 |
| 上传乐享 | 可以 | 乐享官方 MCP |
| 抓视频号内容 | **不行** | 纯 SPA，只记标题，禁止编造 |

视频号那条特别值得说：分享页是纯 SPA，网页端 `get_feed_info` 直接 401，`yt-dlp` 报 Unsupported URL。要拿内容得借登录态、提音频、跑 ASR，登录态还会定期失效。

所以 SKILL.md 里写的不是「视频号抓不到」，而是 **"只记标题和链接，标注「视频，未精读」，禁止编造内容"**。「抓不到」是描述，AI 会尝试绕；「禁止编造」是约束，AI 会停下来标注。

## 为什么链接这一环不做自动化

这是全链路里唯一没有好办法的地方，最后的结论是**不做**。

企业微信群有官方会话存档 API（`sync_msg`），但门槛高：企业认证、超管开通数据与智能专区、配置公钥、自建应用申请权限，且只能拉 5 天内记录。个人微信群则完全没有官方接口，只剩 chatlog（读本地加密数据库）或抓包 hook，微信大版本升级常常失效。

中途试过把 chatlog 收进包里当「可选增强」，v2.4.0 把它整条删掉了，理由三条：

1. **从没跑通过**——本机 `~/.chatlog` 不存在、端口 5030 无响应，那套代码是照文档写的，没经过实测。
2. **权限和收益不成比例**——扫微信进程内存取 SQLCipher 密钥，只为省每天 30 秒的复制粘贴。
3. **留着就是假承诺**——分发包里带一条自己都不用的路径，接收方迟早会踩。

判断「这一环该不该自建」的标准不是能不能做，是为它承担的风险配不配得上省下的时间。代价是每天一次复制粘贴，换来的是微信升级不会让链路失效、分发包里没有自己都没验证过的东西。

## 值得复盘的地方

**一是最初的技术误判让产品方向整个偏了两级。** 看到公众号正文图片是懒加载，就认为必须上 Playwright 渲染 JS，进而觉得「抓取太重、不值得做」，退回到只记标题的第一代架构。实际测试：带浏览器 UA 的普通 HTTP 请求返回 200，正文 4210 字，标题、公众号名、发布时间全在。**文字内容不依赖 JS。** 这一个假设错了，前面两代架构的功夫全废。

**二是返回 `succeeded` 不等于成功。** 乐享的 `update_content` 用「上一段结尾句」做锚点追加，如果锚点后面还有别的块，新内容会被追加到文档**末尾**，原来锚点后面那个块反倒被推到新内容之后——而且接口返回 `succeeded`。这个只能靠回读发现，且回读必须用 `render_mode=mdx`，默认的 markdown 看不到块边界。

**三是静默失败比报错危险得多。** 同名覆盖丢文章、乐享写错位置、配置字段改了不生效，这三个都没报错，都是「看起来成功了」。共同解法是让每一步都有可观测的结果：回读、动作标记、断言。

**四是能力边界要写进文档，而不是靠 agent 临场判断。** LLM 有个稳定的失败模式：Prompt 里有「提炼要点」，看不到内容时它就会根据标题编。所有「拿不到」的分支都要显式禁止输出。

## 当前状态

| 项 | 状态 |
|---|---|
| 拿链接 | 人工投喂（设计选择，不是缺口） |
| 抓正文 | 全自动，HTTP 直取 |
| AI 精读 | 五段结构，写作规范约束 |
| OneDrive | 一篇一文件、标题简写命名 |
| 同名冲突 | 同篇覆盖、异篇另存，不再丢文章 |
| 乐享 | 每日资讯 / 按月分目录，一篇一文档 |
| 定时任务 | 未接调度，要每天自动跑得配 automation |
| 分发 | 39 KB 自包含 zip，含接收方说明与 agent 执行清单 |

## 后续维护方向

- 接调度：链路上支持批量，只是没挂 automation，要每天自动跑得补上定时触发。
- 抓取限速与退避重试：一次打开几十条容易触发风控（会明确报「环境异常」，但不会自动降速）。
- 精读稿质量校验：禁用套话清单目前是写给模型的，不是脚本检查的，这一环只能靠人抽查。
- OneDrive 里还留着旧的合并日报，内容已拆成独立文件，等确认后清掉。

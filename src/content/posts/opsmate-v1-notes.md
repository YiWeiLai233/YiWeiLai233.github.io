动手之前先翻了一遍 GitHub 上做 IT 运维 agent 的开源项目。看得比较细的有几个：k8sgpt 有约六十条规则分析器，结构值得参考；holmesgpt 是 CNCF 项目，工具定义的方式最值得学；ongrid 跟我想做的最接近，走的是双层 agent。前后浅克隆了七个，三百多兆，没进仓库。

看完一个比较明显的印象是，这类项目大多集中在两个地方：Kubernetes 和可观测性。接上 Prometheus、Loki 之类让模型读指标和日志。这条路走得通，因为 K8s 有结构化 API，数据是干净的。

但实际运维里遇到的事，很多不在这一层。服务起不来要看 systemd 的依赖和退出码，机器突然卡要看 dmesg 里 OOM killer 的现场，连接数爆了要数 conntrack，nginx 改完配置要确认加载的到底是哪份文件。这些都在主机上，手上只有文本输出。

所以第一版的范围定在主机侧，功能砍到 Linux、Docker、Nginx 三块。原本列了十项，k8s、网络、防火墙、JVM、Node.js、监控通知都写进 roadmap。全做等于全做不深。

## 命令不能靠正则判断

`policy.py` 负责判断一条命令能不能只读执行。第一版是拿正则去匹配整条命令字符串，写完觉得差不多能用。

后来读了 ongrid 的 cmdpolicy，发现它压根不用正则。它先手写一个 tokenizer 把命令切成 argv，碰到重定向、分号、`&&`、`$()`、反引号、未闭合的引号就直接报错；然后按二进制分类，mixed 类的再按子命令和参数判读写；最后拿切干净的 argv 去执行，不经过 shell。

自己试着找反例就明白了：`systemctl status nginx; rm -rf /` 能被正则的前缀匹配放过去。这类绕过补不完，只能从结构上拒绝不认识的形态。

整个文件重写成 569 行，是全项目最大的单文件。判读写改成写优先，因为 `ip link set eth0 down` 的写动词在第二位，只看首词会漏判成只读。

## 只读先跑通，写操作等人批

写操作不是不能做，是必须有人看过再做。第一版的处理是：模型把命令、风险等级、回滚方式写进报告的处置建议，CLI 抽出来逐条问。

这里用了 langgraph 的 `interrupt()`。用意是一旦有写操作就停在节点里等人输入，批准后从断点接着跑，而不是让模型自己决定什么时候动手。

审批粒度按动作算，一条命令批一次。危险级的动作要再输一次编号确认。非交互环境下危险动作一律按拒绝处理，`--yes` 只跳过安全动作的确认——它不该成为绕过危险确认的后门。

## 测试抓出的几个漏报

四百多个测试里有几个是真问题，而且都在安全侧。

危险命令的黑名单里混着大写，比如 `iptables -F`、`nft flush`。但比较之前字符串已经 `lower()` 过了，所以这两条永远匹配不上，最该拦的反而没拦。

从报告里抽动作的函数，原来用"上一块里有没有命令行"来判断要不要开新块。结果一段里写了 `rm -rf /var/log/app/*.log` 之后，这条被并进上一块，整条消失。抽不到动作意味着这条危险操作永远不会提示人。后来改成只看行首缩进判层级。

`docker_logs` 为了合并容器日志在命令末尾拼了 `2>&1`，但 tokenizer 把重定向当 shell 操作符，命令直接被拒，功能等于没上线。改成在 ssh 那一层合并 stdout 和 stderr。

还有一个是准备测真机的时候才发现的。`host_ip` 一直在跑 `ip -br addr`，而只读策略只认"子命令在最前面"的写法，`-br` 挡在前面就判成无法判定、直接拒掉。更麻烦的是拒绝原因被当成正文，拼进了数据段落。模型拿到的是伪装成地址数据的拒绝消息，几百个测试全绿，真机上一直喂空气。同类问题还有 `systemctl --failed` 也被拒，而这恰好是排查服务起不来最常用的命令。

## langgraph 没写进文档的三件事

审批这块文档读不出关键语义，写了两个探针脚本实跑，跑完删了。

`invoke()` 撞到 `interrupt()` 的时候不抛异常，正常返回，只是返回的状态里多一个 `__interrupt__` 键。照着直觉写成 try/except 会一直等不到。

恢复执行时节点会从头重跑一遍。探针日志里 `gate:enter` 出现两次才确认这件事。这意味着 `interrupt()` 之前写的代码会执行两遍，所以执行命令、切计数、落库全都得放在它后面，否则用户批一次、命令跑两次。

`SqliteSaver` 不支持 `with` 语句。得手动 `sqlite3.connect`，传给 `SqliteSaver`，调 `setup()`，用完自己 `close()`。

第二条要是没验证，代码测试全绿、逻辑全错，而且只在用户真的点了同意的时候才暴露。

## 复盘

这一版最大的未知是没在真机上跑过。四百多个测试用的都是假 executor，真实 SSH 连上去之后诊断质量怎么样、提示词调得准不准、模型会不会编，一次都没验证。现在所有的信心都建立在测试全绿上，而测试喂的是假数据。

审批断点现在只活在进程内存里。进程一退，待批的动作就没了。`checkpoints.db` 是落盘了，但没有任何代码从磁盘把它捡回来，跨进程续跑是后面的事。

工具预算定在 15 次是估的，没测过够不够查一个真实故障。

从报告文本里抽动作这件事本身是脆的。模型不按格式写就抽不到，抽不到就静默不执行。安全方向没错，但可用性有隐患，长期应该换成结构化输出。

下一步先找台真机，或者用 docker-compose 起几个故障场景跑通，把提示词和判定树调准，再谈扩展。提权申请流也要先跑通——磁盘满、Docker OOM 这类最常见的故障恰恰要读 dmesg 和 `/var/log`，没权限就是查不下去。

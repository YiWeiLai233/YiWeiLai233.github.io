双击关标签是一个 Manifest V3 扩展：在网页内容区双击就关掉当前标签。29 个提交里，有 5 个是 `fix`，其中 3 个在修同一个问题——**注入**。这篇只讲怎么坏的。

## 一、防重复注入的标记，成了新脚本的拦路虎

第一版内容脚本开头写着：

```js
if (window.__dblclickCloseTabLoaded) return;
window.__dblclickCloseTabLoaded = true;
```

这个保护本身没问题。问题出在后面的需求上：扩展刚装上时，之前开着的标签里没有内容脚本，用户双击没反应，而人不会想到要刷新页面。所以 `e5ce86c` 加了 `onInstalled` 时把 `content.js` 补注入到所有 http/https 标签。当时我特意让补注入**不受那个标记阻挡**，以为这样就够了。

不够。扩展在 `chrome://extensions` 里点「重新加载」之后，旧内容脚本仍挂在页面上，但它的 `chrome.runtime` 已经失效，消息发不出去。后台补注入新脚本，新脚本看到 `window.__dblclickCloseTabLoaded` 为 true，**直接 return 了**。页面上只剩一个发不出消息的死监听，双击毫无反应。

最难受的是这个状态和「没注入」在外部表现上完全一样。第一版补注入修的是「页面里没有脚本」，这一版才意识到还有「页面里有脚本，但那个脚本是死的」——两种情况的表象一致，判据不同。

`21f0dc6` 的改法：新脚本不再因为看到旧标记就退出，而是找到上一实例调 `destroy()`，摘掉它的监听（`removeEventListener` 两处 + `chrome.storage.onChanged`），再装自己。同时留了个 `alive()` 探针，用 `chrome.runtime.id` 判断上下文还在不在；捕获阶段收到点击时如果发现自己已经死了，就自己摘掉监听，别挡着后面注入的实例。

到这里我以为修完了。

## 二、第二个判据：活着不等于对

两天后加「可自定义双击间隔」，版本升到 1.2.0。功能上线后我自己测发现不生效——老页面里那份 1.1.0 的脚本**活得好好的**，`alive()` 返回 true，`ensureInjected` 判定「已经注入过」，跳过了重新注入。页面跑的还是不支持间隔配置的老逻辑。

`888a25d` 才补上正确判据：探针不能只回答「还活着吗」，要返回**自己的 BUILD**，和 `chrome.runtime.getManifest().version` 比对，不一致就重新注入。

```js
const build = await probe(tabId);
if (build === chrome.runtime.getManifest().version) return false;
return inject(tabId);
```

代价是多了一个手工同步点：`content.js` 里的 `BUILD` 常量必须和 `manifest.json` 的 `version` 一致。两者不一致的后果是每次打开页面都白重注入一次——不会坏，但会一直发生。我在常量旁边写清了这个耦合。

三次修复的共同点：**我每次都在用「有没有」这个二值去回答一个需要三态的问题**。第一版问「注入过没有」，第二版问「活着没有」，第三版才问对——「跑的是不是当前版本」。前两版的判据都不是错的，是不够用。这类 bug 只在状态发生转变时暴露：装上时、重载后、升级后，每个时刻的「旧脚本」含义都不一样。

## 三、双击自己就会选中一个字

「双击前已经有选中文字就不关」这条判断，第一版挂在 `dblclick` 事件上查 `getSelection()`。结果一次都关不掉——**双击这个动作本身就会选中一个词**，浏览器在第二次 `mousedown` 时已经把选区做好了，等到 `dblclick` 阶段再查必然非空。

修法是取快照：在第一次 `mousedown`（`detail === 1`）时记录一次选区状态，`dblclick` 阶段用的是「双击开始前」的值。

后来为了做自定义间隔改成自己配对两次 `mousedown`，这个快照逻辑反而更自然了——`pending = { t, x, y, selectionBefore }`，快照直接跟着第一次点击存。原来的写法算是一种绕路。

顺带记一个同源的事实：**原生 `dblclick` 的等待上限由操作系统的「双击速度」决定**（Windows 默认 500ms），页面脚本既读不到也改不了。所以只要还用原生事件，「自定义双击间隔」在原理上就不可能实现，只能自己配对 `mousedown` 比时间差（`cfg.dblclickMs`，120–1000ms，默认 400）和位置差（`SAME_SPOT = 12` 像素内才算同一次）。这一条不是 bug，但我确实一开始以为原生事件能调。

## 四、Chrome 137+ 把 `--load-extension` 静默吃掉了

端到端测试要真装扩展。第一版用 `--load-extension=<path>` 启动 Chrome，测试跑起来——全绿。

但那是假的。stderr 里有一行：

```
--load-extension is not allowed in Google Chrome, ignoring.
```

Chrome 137+ 的正式版**直接忽略**这个参数，扩展压根没加载。测试跑完给出的是「13 条用例的结果」，其中没有一条真的装了扩展——它测的是「扩展不存在时页面会怎样」。而「扩展不存在」这个前提，恰好让一部分断言天然成立：凡是断言「这里双击不该关标签」的用例，没有扩展时全都通过。

判据其实是有的，只是我第一次没看 stderr，只看了退出码。现在改成浏览器级 CDP 命令：

```js
const loaded = await browser.send('Extensions.loadUnpacked', { path: EXT });
if (loaded.error) throw new Error(`Extensions.loadUnpacked 失败：${JSON.stringify(loaded.error)}`);
```

装载失败直接抛异常，不再有「静默全绿」这条路。

## 五、测试自己的三处静默失败

`d7727c2` 那一条提交的说明是「修两处测试自身的毛病」，实际修了三处，每一处都是**不报错的错**：

**没有超时的 RPC。** `Session.send` 原本等对面回消息，对面不回就无限挂起。整个测试进程卡死，不输出、不失败、不退出——我盯着终端以为是慢。加了 15s 超时后才看到真实的报错。

**CDP 的 target id 和 `chrome.tabs` 的数字 id 不是一个东西。** 前者是十六进制字符串，后者是整数。我把 target id 直接拼进表达式里求值，变成了非法标识符。改成在扩展侧遍历标签、用 `executeScript` 反查跑着目标脚本的那个。

**内容脚本看不见。** 内容脚本跑在扩展的**隔离世界**里，主世界的 `window` 上根本没有 `window.__dblclickCloseTab`。要检查页面里那份脚本是哪个版本，得先 `Runtime.enable` 收集 `executionContextCreated`，按 `origin` 挑出 `chrome-extension://<id>` 那个上下文再求值。

还有一条不算失败但值得记：测「保留最后一个标签」时必须**真的把窗口收到只剩一个**。只断开 WebSocket 不会关标签，前一个用例的页面还开着，测出来的不是单标签场景。

## 如果重来

**给「保护性判断」设计失效路径。** `if (window.__x) return` 这类守卫，写下的时候就要回答：如果这个标记是对的但持有它的实体已经死了，会发生什么？三个 fix 全是在补这个问题的答案。更省事的做法是让标记本身携带足够的信息（版本号），一次问清楚，而不是分三次把二值判断扩成三态。

**静默通过比失败更危险。** 这一轮里真正浪费时间的是两个「看起来成功」的时刻：Chrome 忽略 `--load-extension` 之后的测试全绿，和没有超时的 RPC 卡死。两者都不报错。现在的规矩是：测试框架里任何等待都必须有超时，任何「装载/注入」动作都必须能在失败时抛异常。

**断言要写正向。** 「不关」这类断言在组件不存在时天然成立，等于没测。现在每条用例都成对写：间隔小于上限要关、超过上限不关；正文双击要关、链接上双击不关。成对之后，扩展没装好就会有一半立刻红。

这是微信资讯精读 Skill 从 v1.1.0 到 v2.4.0 的踩坑记录。架构层面的教训写在[另一篇](architecture)里，这篇只讲具体怎么坏的、怎么找到的、怎么修的。

| 版本 | 主要改动 |
|---|---|
| v1.1.0 | 单篇抓取链路打通（抓 + 精读 + 落盘） |
| v1.2.0 | 标题简写命名，替代日期+序号 |
| v1.3.0 | 同名不覆盖 |
| v1.4.0 | 正文提取回退清理页头页尾 |

## 一、抓取：参数被编码两次

**现象**：抓回来的正文被截断，比如某篇只拿到 800 字左右，实际 4000+ 字。

**原因**：URL 是 `https://mp.weixin.qq.com/s?__biz=Mzk...&mid=...`，对脚本参数做了 `urllib.parse.quote(url, safe='')`。链路里 `requests` 又编码了一次，`&` 变成 `%26`，服务端看到的是残缺参数，返回文章开头就 "环境异常" 占位。

**修复**：URL 原样传参，不手动 quote。

**同类坑**：投喂解析正则用了 `.*?(?!...)` 想排除 `https://` 里的 `//`，负向断言在这里无效。换成在 split 后逐行判断，以 `https://` 开头才当 URL。

**另一处**：JS 里 `new URL()` 遇到非法字符串直接抛异常而非返回 null，必须用 try/catch 包。Python 的 `requests.get` 遇到非法 URL 同样抛异常，得先判断可解析再发请求。

## 二、AI 精读：两次跳步

**第一次**：用 `trae-agent` 研究，Agent 完全跳过页面导航，直接从缓存输出。判据是不看截图分辨率去推断，要看 window size 和 screenshot size 比值——比值远小于 1 说明画面被大幅缩放，实际导航发生的判断不可靠。

**第二次**：同一模式复现，还擅自用内置 web search 替代本地 skill。判据：browser 工具调用记录里只有 0–1 次，但产出很"完整"。这类的特征是**输出比输入还详尽**。

**修复**：SKILL.md 里加硬性检查——"不要用内置搜索工具替代本 skill、每次推进前必须截图确认"。

**深层原因**：agent 的调用链里，如果某一步的产出看起来已经像最终结果，"中间步骤就会被优化掉"。所以约束必须写成"先做 A 才允许做 B"，而不是"记得做 A"。

## 三、结构：同名文件导致丢文章

修改 `publish.py` 前发现的一个设计缺陷：用「标题简写」作为去重键。

```
今天抓了 10 篇，其中两篇标题都叫「技术日刊」
→ 第二篇直接跳过，静默丢失
```

这是最常见的丢数据形式——不报错、不告警、看起来一切正常。

**修复**（三选一，选了 ③）：

① 加随机后缀 → 文件名不可读
② 用完整标题 → 文件名太长，Windows 超 255 字符
③ **标题简写 + 内容判定** ← 采用

```
两篇重名标题，比较正文前 N 字：
  - 正文相似度 > 阈值 → 视为同篇，跳过（幂等）
  - 差异明显 → 视为不同文章，存为「标题-日期.suffix.md」
```

关键是**先判断再落盘**，不是"存在即跳过"。这个问题在网页版抓取上更明显——同一篇文章可能因为编码差异被当成新文章重复存（`intcmp` → `intcmp&scene=21`）。

## 四、乐享：三个坑，两个静默

**坑 1 · HTML 直接塞进 XML 参数**

```
错误: Failed to call tool (code 1000004)
```

原因是把 markdown 原文（含 `<br>`）直接塞进 `entry_import_content`。即使 title 里避开 `<` `>`，正文里的 HTML 一样会让请求的 XML 体坏掉。

**修复**：两个字段都先 base64 编码，临时文件名也加后缀：

```python
base64.b64encode(md_content.encode()).decode()
source_name=f"{纯文件名}-{ts}-{os.getpid()}.md"
```

文件名带后缀，乐享才按 markdown 正确解析。

**坑 2 · 整页写入失败**

v2.0.0 初版失败结论是"乐享 MCP 不能写内容"。实际测试：用 v1.x 的纯文本 md 直接写入**成功**，说明工具本身能用，是个别文档内容触发问题。

进一步判断：脚本从正文里取了 5 个字符当 title/category 前缀，很可能混进了隐藏字符或控制字符。**A/B 测试**：换成固定英文前缀后，用同样的 md 文件重试，成功。

**结论**：给乐享的 title 只放固定的时间戳，正文只放纯 markdown，不塞从正文里截出来的动态字符串。

**坑 3 · 追加成功但位置错（最贵的一个）**

v2.1.0 的当日汇总文档是"段式追加"设计：

```
文档结构：[标题块] [段 1] [段 2] [段 3]
追加逻辑：在「上一段结尾句」后插入新段落
```

问题：乐享的 `update_content` 是按「块位置」插入的。如果「上一段结尾句」后面还有别的块，新内容会被插入到**那个块后面**——如果预期位置是文档第 N 块，但文档里只有 N-1 块，会插错或者无效。

更糟的是实测发现插入位置索性落到了文档末尾：

```
文档：[标题] [段1] [锚点句] [段2]
追加段3（锚点=段1结尾）
结果：[标题] [段1] [锚点句] [段3] [段2]  ← 段3 跑到了段2 前面
```

而接口返回 `succeeded`。

**修复**：追加后回读文档全文，校验新段落是否出现在预期位置；不出现则整篇重写，并用 `tags` 标记版本应对并发写。回读要注意 `render_mode=mdx`，默认 markdown 看不到块边界。

## 五、追加 idempotent 反模式

v2.1.0 用了 `append_content` 逐段追加。这个操作的语义是"追加"，**不是"确保存在"**。重试一次就多一段。

**正确做法**：先读文档，判断这一段的钩子（日期+标题）是否存在；存在就跳过，不存在才追加。

这条在 v2.2.0 改成整页写入之后才彻底解决，同一个脚本重跑多少遍结果都一样。

## 六、Windows 路径与 PowerShell 的坑

- 直接用 `os.path.expanduser("~/Documents/...")` 拼出 `%USERPROFILE%` 字符串传给 OneDrive，不是展开后的路径。**手工展成绝对路径**。
- SKILL.md 里写的命令用 `python scripts/xxx.py`——但 PowerShell 下 `python` 可能不在 PATH。用 `py -3` 在 Windows 上更稳，又容易在 Linux 上不适配。最后是两者都兼容地查：

```powershell
if (Get-Command python -ErrorAction SilentlyContinue) { ... } else { py -3 ... }
```

- 没有显式处理参数的脚本，**默认应当跑全流程**，不要去写空跑参数。用户第一次装就不会用 `--dry-run`。

## 七、决定删掉的每一样东西

v2.4.0 把大量功能删除。每一个都是想清楚了才删：

| 删除项 | 理由 |
|---|---|
| 投喂到乐享的原生入口 | 乐享入口与 OneDrive 不同步，反正常用是从 OneDrive 上传 |
| chatlog 微信采集 | 从没跑通过；要微信进程内存读取权限，拿到的收益仅是"免手动复制链接"，不成比例 |
| HTML 投喂工具 | 第一代产品遗留，实际使用率 0 |
| team 模式 | 需求理解错（"把内容分发给别人"理解成了"把工具分发给别人"）的产物 |
| 红黄绿视觉设计系统 | 合并日报时代的产物，改成一篇一文件后就无意义了 |

**判断标准**：这个功能有没有在真实使用中出现过？没有就是负担。留着一条自己没验证过的路径，接收方迟早会踩。

## 如果重做一遍

1. **第一天 curl 公众号页面**，而不是先设计数据结构。
2. **第二句话就问清"浓缩的原料是什么"**。
3. **环境自检脚本先写**，把"哪一环能通"摊开来。
4. **别用「标题+序号」当文件名**，用标题简写并配同名区分。
5. **乐享的写入限制先实测**：HTML 塞 XML、中间插入错位，这两个坑各花了几十分钟，但一次 20 分钟的实验就能全部暴露。

## 核心结论

**静默失败比报错危险得多。** 同名覆盖丢文章、乐享写错位置、配置改了不生效，这三个都没报错，都是"看起来成功了"。

共同解法是让每一步都有可观测的结果：回读、动作标记、断言。**AI 的输出也要盯着，因为它也会用"看起来对"来掩盖"没做"。**

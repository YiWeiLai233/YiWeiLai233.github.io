最初的诉求是"研究腾讯乐享怎么自动收集我每天发在群里的视频号和公众号资讯，再让 WorkBuddy 自动浓缩成 markdown 放到公司 OneDrive"。

听起来是一件事，实际是四个环节，每个环节的可行性差别很大。而需求澄清的过程本身，就是这个项目最重要的一半。

## 三轮才问对

| 轮次 | 用户说的 | 我当时的理解 | 实际要的 |
|---|---|---|---|
| 1 | 自动收集群资讯，浓缩成 md | 抓链接 → 记录标题和推荐语 → 汇总 | ❌ 只要链接和标题，没有内容 |
| 2 | 不只是本地用，想分发别人 | 做成团队共享的合并日报 | ❌ 方向错了 |
| 3 | 要根据**内容**浓缩，不是投喂模式 | 明白了：要读正文全文 | ✅ 抓正文 → AI 精读 → 双存储 |

第三轮之后才真正对上。前两轮做的投喂工具、团队合并日报，大部分被弃用。

**教训：当需求里出现"浓缩""提炼""总结"这类词，先确认原料是什么。** 只有标题和链接，AI 只能复述标题，那不是浓缩，是编造。

## 第一代 · 搬运工（已废弃）

```
群消息 → 投喂区 → 正则解析 → 日报（标题+推荐语+链接）→ OneDrive
```

**假设**：资讯的价值在"知道有这么一篇文章"，记下标题和链接就够。

**为什么废掉**：用户要的是内容浓缩。标题是原文作者写的，日报读者看了还是要自己点进去。这套东西的唯一产出是一堆链接列表，和自己刷微信没区别。

这一代剩下的资产：宽容解析器（能扛住各种乱七八糟的粘贴格式）、URL 去重、标题简写提取。这些后来都保留了。

## 第二代 · 团队合并（方向性错误，已废弃）

```
多人投喂工具(HTML) → 共享文件夹 → 定时扫描 → 团队合并日报
```

**假设**：用户说的"分发给别人用"是要生成一份全员可见的团队日报。

**为什么废掉**：用户真正要的是"把这套**能力**给别人用"，不是"把这份**内容**给别人看"。做的是工具分发，理解成了内容分发。连带做的一堆东西（单文件 HTML 投喂工具、team 模式合并、贡献统计）全部闲置。

这一代唯一的沉淀是一个副产品结论：**公共文件夹里的文件绝不能移动或清空**。那是别人正在看的目录，动了会出事。判断"是否处理过"只能靠状态文件，不能靠归档动作。这条后来还真的用上了——`publish.py` 的幂等设计受益于此。

## 第三代 · 精读归档（当前）

```
链接 → 抓正文 → AI 读全文 → 一篇一个 md → OneDrive + 乐享
```

**关键转变：一天一份合并 md → 一篇一个文件。**

第一反应是"一天一篇汇总比较整齐"，实际是错的：

- 知识库的价值在检索。一篇塞十条，RAG 召回会返回一整天的流水账。
- OneDrive 上一天一个文件，找某篇文章要打开一整天的文件翻。
- 一篇一文件，文件名就是标题简写，两边都能直接找到。

`publish.py` 里甚至专门写了跳过逻辑：批量同步时跳过纯日期命名的 md，因为那是旧版日报格式，不该当单篇文章传。

## 那个把方向带偏的误判

抓公众号正文，我最初判断**必须上 Playwright**。

理由是看到正文图片是懒加载，就想当然认为内容也靠 JS 渲染。实际测试：

```
HTTP 200，完整 HTML，正文 4210 字，
标题、公众号名、发布时间全在，无任何反爬验证。
```

**文字内容不依赖 JS。** 图片确实要 JS，但精读稿要的是文字。

这个误判的代价不是多写了一层浏览器，而是**整个方案被做轻了**——因为觉得"抓取太重，不值得做"，才退回到只记标题的第一代架构。一个技术假设错了，产品方向整个偏了两级。

教训写进 SKILL.md 了：不要因为渲染相关的迹象（懒加载、SPA 外壳）就推断内容拿不到，**先用 curl 试一次**。

## 附带的两个"其实不用做"

**OneDrive 不需要任何 API 授权。** 一开始在想 Microsoft Graph 的 OAuth 流程。想复杂了——OneDrive 客户端本来就把同步目录挂在本地，直接往里写 `.md`，客户端自己上传。不需要注册应用、不需要令牌、不需要处理续期。

代价只是：必须在装了 OneDrive 客户端的机器上运行，且目录真的在同步根下。这一点 `check_env.py` 会检查——如果配成了普通本地目录，会明确警告"文件不会上云"。

**乐享不是普通 MCP。** 它不直接暴露业务工具，要走元工具三步：`search_tools` 找工具名 → `get_tool_schema` 拿参数 → `call_tool` 执行。第一次接触按普通 MCP 的思路去找 `entry_create_entry`，找不到，还以为是没连上。

## Skill 必须自包含

第一版 Skill 只是个壳，脚本指向 `daily-digest/` 项目目录。别人拿到装不上——路径是死的。

改成：所有脚本的根目录就是 Skill 自己，`config.json` 与 SKILL.md 同级，缺失时从 `config.example.json` 自动生成。

**判断标准很简单：把整个文件夹复制到另一台机器，能不能直接跑。**

## 如果重做一遍

1. **第一天就去 curl 公众号页面**，而不是先设计数据结构和日报格式。
2. **第二句话就问清"浓缩的原料是什么"**，标题还是正文。这一问能省掉两代架构。
3. **一开始就一篇一文件**，不做合并日报。
4. **先做一个 `check_env.py` 级别的环境探测**，把"哪一环能通、哪一环要降级"摊在桌面上。
5. **乐享的写入约束提前实测**，整页写入失败、中间插入错位这两个坑，各花了不少时间试错，而它们都可以在一次 20 分钟的实验里全部暴露。

核心可以压缩成一句：**先探清整条链路上每一环的真实可行性，再决定做什么形态的产品。** 这个项目的两代废弃架构，都是因为跳过了这一步。

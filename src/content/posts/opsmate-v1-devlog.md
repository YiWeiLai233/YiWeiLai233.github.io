本来没打算一天做完，结果一路写下去停不下来。收工时数了下：31 次提交，34 个模块文件 6083 行，13 个测试文件里 472 个测试。

这篇文章记的是当时怎么想的。三个月后回来看，`git log` 能告诉我改了什么，但告诉不了我为什么不用正则匹配命令。

## 动手前先看别人做到哪了

没直接开写，先翻了一圈 GitHub 上的同类项目。

| 项目 | 星数 | 语言 | 大致印象 |
|---|---|---|---|
| k8sgpt | 8275 | Go | 六十来条规则分析器，结构值得抄 |
| kubectl-ai | 7593 | Go | 绑死 K8s |
| kagent | 4090 | Go | 同上 |
| holmesgpt | 3680 | Python | CNCF 的，toolset 设计最值得看 |
| ongrid | 1221 | Go + TS | 跟我想做的最像 |
| AIOpsLab | 1019 | Python | 测评基准，不是产品 |

前七个浅克隆到本地翻了翻，三百多兆，加进 gitignore 了。

看完有个挺明显的感受：这些项目几乎全在做 Kubernetes 和可观测性。Prometheus、Loki、Tempo，三件套接上，然后让模型去读指标和日志。这条路走得通，因为 K8s 有结构化 API，数据是干净的。

可我在实际运维里遇到的事，很多根本不在那层。服务起不来，得看 systemd 的依赖链和退出码；机器突然卡，得摸 dmesg 里 OOM killer 的现场；连接数爆了，得数 conntrack；nginx 改了配置没生效，得确认到底加载的是哪份文件。这些都是主机上的事，手上只有一堆文本输出。

所以我把方向定在主机侧。不是因为别人想不到，是因为不好做——没有 API 可依，解析全靠自己。但难做的地方才轮得到我。

## 先把范围砍到能做完

用问答的方式跟需求对齐，前后定了十五条决策，写进 `docs/design.md`。挑三条影响最大的说。

第一条是把范围砍到 Linux、Docker、Nginx 三块。原本列了十项，还有 k8s、网络、防火墙、JVM、Node.js、监控、通知。全做等于全做不深，先把三块做透，剩下的扔 roadmap。

第二条是第一版只做只读诊断，写操作必须人工确认后才执行。想过要不要一步到位做自动修复，后来否了。一个会在生产机上自己动手的 agent，第一版没人敢开。

第三条是选 LangGraph。理由就一个：它的 `interrupt()` 加 checkpointer 恰好就是"执行前停下来等人批、批了从断点接着跑"这套东西。自己写这个状态机不是写不出来，是很容易写错。当时觉得省了事，后来才发现这套东西的坑也不少，后面会说。

## 写到一半，把最大的那个文件推翻了

`policy.py` 是判断"这条命令能不能只读执行"的模块。第一版我用正则匹配整条命令字符串，写了大半天，感觉差不多能用了。

然后去看了 ongrid 的实现，发现人家压根不用正则。

他们的做法是手写一个 tokenizer，把命令切成 argv，重定向、`;`、`&&`、`$()`、反引号、没闭合的引号，碰到任何一个直接报错。然后把命令按二进制分类，read-fs、read-system、mixed、network、denied。mixed 类的再按子命令和参数判读写。最后拿切干净的 argv 去执行，压根不过 shell。

我当时第一反应是"至于吗"。然后自己想了个反例：`systemctl status nginx; rm -rf /`。正则匹配到开头的 `systemctl status`，放行了。

这类东西想不完。你补一条规则，就有另一条绕过。最后只能承认：结构上不认识的，一律拒绝。正则表达不了"这条命令的整体结构对不对"。

于是整个文件推倒重写，569 行，成了全项目最大的单文件。

重写的时候有个细节踩了一下：判读写不能只看第一个词。`ip link set eth0 down`，写动词在第二位，只看首词会判成只读。所以逻辑是写优先——先看有没有写动词，再看能不能只读。

## 顺便从别人那儿抄了两样东西

一个是 holmesgpt 的 toolset 写法：一个 YAML 文件描述一组工具，每个工具就是一条命令模板加参数说明。这启发了我把工具做成"命令模板 + 参数校验 + 统一执行通道"。

另一个是他们放在 `CLAUDE.md` 里的一句话，大意是"服务端过滤至关重要，永远不要从 API 返回无界数据"。他们有个查分片的工具一次返回全部 shards，一口气吃掉两万五千多 token。我看到这句的时候正在纠结要不要给输出设上限，看完就不纠结了，定了 8KB。

## 写的顺序

基本是上一步不扎实就不往下走：

1. `config.py` — 配置分层、主机清单、sudo 白名单
2. `ssh.py` — 长连接、跳板机、超时、按字节裁剪
3. `policy.py` 和 `privileges.py` — 只读判定、三级权限、提权申请单
4. `tools/` — 32 个只读工具，linux 14 个、docker 8 个、nginx 7 个、知识库 3 个
5. `runbooks/` — 8 份故障判定树，一份五六十行，写的是判断顺序不是结论
6. `store/` — SQLite 七张表
7. `notify/` — 飞书、钉钉、企微、邮件、webhook
8. `agent/` — LangGraph 的图
9. `runner.py` 把上面串起来
10. `cli.py` 和 `mcp_server.py` 两个入口
11. 审批中断

## 测试抓出来的东西

472 个测试不是走过场，抓出了十来个真 bug，有几个我到今天想起来还有点后怕。

危险命令的黑名单里混着大写，`"iptables -F"`、`"nft flush"` 这两条。但匹配之前字符串已经 `lower()` 过了。也就是说这两条永远匹配不上，最该拦的反而没拦。这是个教训：凡是要比较字符串的地方，大小写归一化之后要单独测一遍。

故障判定树的检索一开始返回零分也算命中。我拿"用户头像上传后模糊"去试，居然命中了 nginx-502 和 nginx-504。翻了下原因，判定树的适用说明里有"用户""报告""出现"这种词，随便一句话都能沾上。这个比查不到还坏，模型会以为找对场景了，往错的方向查半天。后来加了停用词，零分直接丢。宁可返回空。

工具预算有个静默漏洞。四个节点各自去 `ctx.get("budget")` 拿预算对象，但测试里我只在 `tool_ctx.budget` 上设了耗尽状态。结果预算明明用完了，命令还在跑。这种"取错地方"的 bug 测试不专门写一条是抓不到的。

还有一处是兜底逻辑自己拆自己的台。零证据的时候我会直接给一份"未能确认"的报告，不走模型。它的证据节写的是"（无）"，而"（无）"恰好在占位符黑名单里，导致这份报告自己过不了自己的检查。最后的防线自己塌了。

从报告里抽可执行动作那个函数也有问题。切分条目的时候，我用"上一块里是不是已经有命令行"来判断要不要开新块。结果一段里写了 `rm -rf /var/log/app/*.log` 之后，这条被并进了上一块，整条消失。抽不到动作就意味着这条危险操作永远不会提示人，属于漏报。后来改成只看行首缩进判层级。

`docker_logs` 为了合并容器日志在命令末尾拼了 `2>&1`，但 tokenizer 把重定向当 shell 操作符，直接拒了。功能上线即失效。改成在 ssh 那层合并 stdout 和 stderr。

进程列表那个工具表头切错了位置，硬取前三行，两行数据被当成表头。这种"看起来完全正常"的 bug 最难发现。

还有一个是准备测真机的时候才发现的，挺丢人。`host_ip` 一直在跑 `ip -br addr`，而我们的只读策略只认"子命令在最前面"的写法，`-br` 挡在前面就判成"无法判定"直接拒。更糟的是拒绝原因被当成正文，拼进了数据段落里。也就是说模型拿到的是伪装成地址数据的拒绝消息，497 个测试全绿，真机上一直在喂空气。

顺带发现 `systemctl --failed` 也被拒，而这恰好是排查服务起不来最常用的命令。

## langgraph 那三个文档里没有的事

审批中断是最后做的一块。文档看了一遍，几个关键点读不出来，干脆写了两个探针脚本实跑，跑完删了。

第一个发现：`invoke()` 撞到 `interrupt()` 的时候不抛异常。它正常返回，只是返回的状态里多一个 `__interrupt__` 键。照着文档直觉写会写成 try/except，然后一直等不到。

第二个才要命。恢复执行的时候，节点会从头重跑一遍。探针的日志里 `gate:enter` 出现了两次，我才确认这件事。意思是 `interrupt()` 之前写的代码会跑两遍。执行命令、切计数、落库，全都得放在 interrupt 之后，不然用户批一次、命令跑两次。

这条要是没验，代码测试全绿、逻辑全错。而且它只在"用户真的点了同意"的时候才暴露，平时根本看不出来。

第三个：`SqliteSaver` 不支持 `with` 语句。得手动 `sqlite3.connect`，传给 `SqliteSaver`，调 `setup()`，用完自己 `close()`。

## 一个自己作出来的事故

我用 PowerShell 的 `(Get-Content -Raw) -replace ... | Set-Content -NoNewline` 批量改 `nginx.py`，把文件写成了非 UTF-8。

之后就读不了了，工具报 invalid UTF-8 text。想覆盖写也写不了，报 file changed since it was read。整个文件锁死。

修的过程挺绕：先删掉，新建一个空文件，读一次让它进入已读状态，然后全量重写。绕了一圈才恢复。

从那以后改源码我一律用编辑工具，不再碰 shell 的字符串替换。那玩意儿不检查编码，不检查行尾，也不进入工具的已读状态管理，出事了还不知道怎么坏的。

环境上还有几个坑。git 把进度写到 stderr 的时候，PowerShell 5.1 会报 `NativeCommandError` 并且退出码 1，但命令其实是成功的。我差点因此把一次已经成功的 push 又重推一遍。另外 `git commit -m` 带多行中文会被拆成多个 pathspec 直接失败，只能把消息写进文件用 `git commit -F`。还有 gh 装好了但不在当前进程的 PATH 里，得用绝对路径调。

## 没什么把握的地方

写下来免得下个版本自己骗自己。

最要紧的是整套东西没在真机上跑过。472 个测试用的全是假 executor，真实 SSH 连上去之后诊断质量怎么样、提示词调得准不准、模型会不会编，一次都没验证。这是目前最大的未知数。

审批断点现在只活在进程内存里。进程一退，待批的动作就没了。checkpoints.db 是落盘了，但没有任何代码从磁盘把它捡回来。跨进程续跑是下个版本的事。

工具预算 15 次是拍脑袋定的，测都没测过够不够查一个真实故障。

从报告文本里抽动作这件事本质上是脆的。模型不按格式写就抽不到，抽不到就静默不执行。安全方向没错，但可用性有隐患，长期得换成结构化输出。

JVM 和 Node.js 还有隐藏门槛。`jstack`、`jcmd` 必须以运行进程的 owner 身份执行，权限层现在没留这个口子。Node 的事件循环滞后更是没有通用的只读手段，得往应用里埋点才有数据。

## 接下来

顺序上我的判断是验证优先于扩张。

先找台真机，或者用 docker-compose 起五个故障场景跑通。现在所有的信心都建立在测试全绿上，而测试喂的是假数据。

然后把提权申请流跑通。磁盘满、Docker OOM 这类最常见的故障，恰恰都要读 dmesg 和 `/var/log`，没权限就是查不下去。这条在 V1 是日常路径，不是边缘情况。

这两件都过了再谈 V2。

题库原本是一个 88 KB 的 Markdown 文件，230 道题按章节排好，每道题后面跟着答案。后来陆续追加了 Linux 运维、CI/CD、Kubernetes、数据库、桌面运维五份专项题库，六份合起来八百多题。直接丢进站点当一篇文章也能看，但"看"和"刷"是两回事——刷题要的是随机抽一题、想一下、点开对答案，然后下一题。所以这次把它做成了交互模块。

## 随机出题没用 Math.random()

第一版很直接：每次点"下一题"，从题库里 `Math.random()` 抽一个 id。写到一半意识到不对——几百题里刷 20 题，按生日问题算，期望撞题一两次。刷题场景里重复出一道刚做过的题，体验比想象中糟得多。

改成洗牌队列：把**筛选范围内**的题打乱成一个队列，游标逐题往后走，走完一整轮再重洗。这样一轮之内绝对不会重复，而且"洗完一轮再来"的节奏本身也符合刷题习惯——先过一遍，第二遍再巩固。

顺带一个反直觉的点：筛选条件一变（比如切到只看 K8s），队列要重建，游标归零。不能保留游标，否则换了章节之后位置对不上，会跳到队列中间去。

## 题库为什么不进 HTML

题库 JSON 现在有 1.4 MB（只有一份题库时是 165 KB）。如果首页把整份塞进 HTML，首屏体积会直接翻倍，而且首页那几张题卡根本用不上那么多数据。

所以拆成两份：

- 页面在**构建期**读题库，只渲染静态部分——总题数、章节分布、考前速记、复习路线。这些内容本来就该被搜索引擎和直接访问看到。
- **题目本体**由 island 在浏览器里 `fetch('/data/interview-bank.json')` 拿，筛选和出题全在客户端做。

代价是刷题区会先显示一句"题库加载中"，但换来的是首页 HTML 不背那几百 KB。

## 两个入口，不同密度

首页那块只要"随手刷两题"的轻体验，所以是紧凑模式：一张题卡、看答案、下一题，加一个"去刷题页"的按钮。筛选条塞进首页会显得很重，而且首页已经有项目、收藏、日志三块内容了。

独立的 `/interview/` 才是完整版：难度、题库、章节三层筛选，进度计数，侧栏放题库概况和速记折叠区。速记那几节（必背端口、必记数字、一句话答案）其实更适合考前十分钟扫一眼，独立页有空间放，首页没有。

首页那块用 `client:visible` 懒水合——首屏没滚到就不加载 Vue 运行时，别为了一个可能没人点的区块拖慢首屏。

## 备份状态存什么、不存什么

筛选项、题库分组、"已刷多少题"以及标记过的题目 id 存 localStorage，跨会话有意义。

**出题位置不存**。因为每次进页面队列都会重洗，硬把上次的游标套回去只会错位——上次刷到第 17 题，这次队列已经重排过了，第 17 位是另一道题。想清楚这一点之后省掉了一整套"恢复进度"的逻辑。

## 「这题不会」其实一直没被记住

题卡答案下面有个"这题不会，记一下"的按钮。有天想回看自己标过哪些题，才发现这个功能从头到尾都是假的——点下去按钮会变粉、文案变成"已记为不会，记得回看"，然后翻到下一题就恢复原样，刷新更是干干净净。

原因是它被写成 `const failed = ref(false)`：一个纯粹的视图开关，`markFailed()` 只做 `failed.value = !failed.value`，落盘那步 `saveState()` 里压根没有它，而 `next()`、`prev()`、重建队列时还各有一句 `failed.value = false`。三个地方都在主动把它抹掉，等于标记最多活到下一次翻页。

修法不是补一句持久化就完事，而是**把状态换掉**：布尔值改成题目 id 集合 `failedIds: string[]`，当前题有没有标记由 `contains(current.id)` 算出来。这样一来切题不再需要重置——不同题的标记本来就该各自独立，那句 `failed.value = false` 是被错误的数据结构逼出来的补丁。

顺带落进 localStorage（跟着筛选项一起存在同一个 key 下），刷新、关标签页都还在。存档里读出来时会过一遍 `typeof === 'string'` 的过滤，防止旧存档里的脏数据把渲染搞崩。

## 标记卡片放在题卡下面，而不是塞进题卡

只有持久化还不够用——标了十几道题，没有一个地方能看见它们，那和没标区别不大。所以题卡下方单独起一张卡片列出已标记的题。

几个细节：

- **按题号排，不按标记顺序**。这是张回看清单，不是操作历史，按题库原顺序翻才顺。
- **点整行跳回那道题**。跳转是在当前出题队列里 `findIndex`，所以题被筛选条件排除时会点不动——这时候给一句"先放宽难度或章节再找它"，比静默无反应好。
- **题干在卡片里去掉了反引号**。题库 827 题里有 130 题题干带行内 code 标记（`` `df` ``、`` `D` 状态 `` 这类），题卡里按 HTML 渲染没问题，但列表里一行只放一句、又是纯文本，反引号很碍眼。
- **列表限高 15rem 内部滚动**。首页那块地方有限，标得多了不能让它把卡片撑到半屏。
- 单条 `×` 取消、右上角整体清空，误点能撤回。

最后一句写在卡片底部：标记只存在这台机器的浏览器里，换设备不会同步。localStorage 的边界提前说清楚，比让用户以为跨端同步、换电脑发现全没了要好。

## 一点收尾

题库源文件放在 `src/data/interview/` 下，唯一的真相是那个 Markdown。`scripts/build-interview-bank.mjs` 在 dev 和 build 前跑一遍，解析成 JSON。想加题就改 Markdown，脚本负责重新切分题干和答案——不用手工维护两份。

## 加第二份题库时踩的坑

后来补了一份 Linux 运维专项题库，没有并进原文件——那份已经近 2000 行，再写进去定位都困难。于是脚本从"读一个固定文件"改成读一组显式列出的文件。

两个坑：

**题号会撞。** 每个题库文件都从 `Q1` 开始，两个文件直接合并就是两套 q1、q2。所以合并时先按文件顺序、章节顺序、原题号顺序入队，全部读完再统一重排成 1..N 的全局题号，`id` 随之重算。

**速记卡不能按章节序号认。** 原来判"这是速记章不是题目章"用的是 `startsWith('十五、')`。第一份文件的速记卡确实在第十五章，可 Linux 题库的"十五、"是正经的 Shell 脚本实战——16 道题被整章吞成速记。改成按标题里有没有"速记"两个字判断，跟序号解耦。

至于为什么是显式文件列表而不是扫目录：题号在合并后是连续重排的，扫目录的话，文件名排序上的一点变化就会把全站题号打乱。

## 同一个坑，第三次踩的是「章节太多」

再往后题库涨到六套：通用运维、Linux 运维、CI/CD 与发布、Kubernetes、数据库、桌面运维。题数从 424 冲到八百多，"能不能解析出来"早就不是问题了，问题是**页面还能不能看**。

章节从 29 个变成 89 个。章节筛选原本是一排平铺的 chip，现在直接糊成一堵墙，找"MySQL 主从复制"得在这一堆里扫三遍。侧栏的章节分布也一样，一屏塞不下。

解法是给每份题库一个分组名（`group`），构建期写进每个章节，前端先选题库、再在题库里选章节：

- `/interview/` 的筛选条多了一行"题库"，章节 chip 只显示选中题库里的，不选就是全部；
- 侧栏章节分布改成按题库折叠的 `<details>`，默认全收着；
- 速记区同样按题库分组——六份速记里"必记参数""一句话速答"这种标题各出现两次，不分组根本分不清哪份是哪份。

这里有个取舍值得记一下：分组名是**手写在脚本的 SOURCES 里的**，不是从 Markdown 标题推出来的。理由和题号一样——分组会直接显示给用户，让它跟着文件走比让它跟着内容猜更可控。

另一个副作用是题库 JSON 从 484 KB 涨到了 1.4 MB。这个体积对按需 fetch 来说还算可以接受（gzip 后更小），但已经在提醒：**再加两套就得考虑拆多份 JSON、按题库懒加载了**，不然下载一次就是全量。

改动都在同一个 commit 序列里：题库模块、island 组件、独立页、首页区块、导航入口，各自独立提交。
